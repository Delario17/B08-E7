# ADR：以提交身份和内容哈希约束 E11–E12 产物

- 编号：B08-241250078-E11E12-01
- 日期：2026-11-28
- 作者：孙博一（241250078）
- 状态：已验证

## 背景

DRAFT、BuildChecker、EChecker 和 MDFixer 在一个任务中传递报告、候选补丁与构建证据。基线和目标属于不同 Git 提交；如果只传文件路径，消费者无法判断报告是否来自正确提交，也无法发现产物在传递过程中被替换。

## 决策

阶段报告统一使用 `schema_version=e11e12-1`，并携带 `kind`、`status`、`commit`、`job_id` 和 `trace_id`。产物引用采用 `artifact://{job_id}/{relative_path}`，同时记录 SHA256 和字节数。消费者在使用报告前校验：

1. 报告状态成功且类型正确；
2. 报告绑定的 Git 提交与当前目标一致；
3. 引用产物的实际内容哈希与声明一致；
4. 修复只在隔离副本中应用，构建和重检通过后才接受。

E11-B 使用课程固定 MD 报告，便于单独验证 MDFixer。E12 使用本任务 `incremental-check` 的真实输出，五阶段共享 job/trace。HTTP 层以幂等键绑定规范化请求：同键同请求复用原任务，同键不同请求返回 409；该绑定需要落盘并在服务重启后恢复。

## 真实项目适配

B08 真实项目采用以前 E3 的 MDFixer Target，profile 为 `b08-e3-target`。准备脚本从历史 base 创建隔离副本和 target，不修改原仓库。DRAFT 生成的实际镜像 ID传递给后续全量检查、增量检查、修复和复验，避免“构建环境”和“检测环境”不一致。

## 后果与验证

代价是报告字段和校验步骤增加，但可以明确拒绝旧报告、错误类型、哈希不一致和幂等键冲突。宏/混合用例证明修复器能保持 Makefile 的抽象结构；旧提交报告返回 `STALE_REPORT`；API 下载的文件哈希、响应头和清单三者一致；新增个人测试证明幂等绑定在重启后仍生效。
