## 1. 输入与缺失依赖

样例包含 `main.c`、`helper.c` 和本地头文件，使用显式 Make 规则。`main.c` 包含 `config.h`，原 Makefile 却声明：

```make
main.o: main.c unused.h
```

固定报告由教学程序 `scan()` 使用 GCC 依赖观察结果与 Make 声明比较得到，版本绑定到样例提交 `e29dace63e36c738403be6c96bc55e3dbe4bbfdc`。报告发现：

| 类型 | 目标 | 依赖 |
|---|---|---|
| MISSING | `main.o` | `config.h` |
| REDUNDANT | `main.o` | `unused.h` |

首次编译可以读取已经存在的头文件并成功，但 Make 未声明 `config.h` 到 `main.o` 的依赖关系。只检查首次构建，不能证明修改头文件后会重新编译。

候选补丁采用 direct 风格，仅补齐缺失依赖，保留冗余依赖和编译配方：

```diff
-main.o: main.c unused.h
+main.o: main.c unused.h config.h
```

## 3. 三次候选判定

`validate()` 在独立沙箱中检查补丁应用、构建、程序输出、头文件变化后的增量构建和缺失依赖。全部通过后才将沙箱中的 Makefile 写回源项目。

| 场景 | patch_applies | build | test | header_change | no_missing | accepted |
|---|---|---|---|---|---|---|
| 错误测试预期 | true | true | false | true | true | false |
| 正常候选 | true | true | true | true | true | true |
| 无效补丁 | 未记录 | 未记录 | 未记录 | 未记录 | 未记录 | false |

错误测试案例故意要求输出 `99`，程序实际输出 `1`。虽然构建、头文件变化和重检通过，功能测试不满足仍导致拒绝；`error=null`，`source_unchanged=true`，`rollback=true`。

正常候选所有检查通过，`accepted=true`，源 Makefile 被更新，因此 `source_unchanged=false`、`rollback=false`。

最后在已修复项目上验证内容为 `invalid patch` 的补丁，`git apply --check` 返回 `No valid patches in input`。`checks` 为空，表示未完成任何成功检查；`source_unchanged=true`、`rollback=true`，已接受版本保持不变。拒绝时源目录没有写入候选，`rollback=true` 表示拒绝后源文件保持原样。
